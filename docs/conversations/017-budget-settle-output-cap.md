# 预算：只累计真实账单、给收尾留钱

## 估算与实耗差了一个数量级，小预算跑不动还白花钱

**意图**：同一条 `review /tmp/1.diff --worktree ~/syscare` 跑两次差距太大——`budget_per_run = 0.1` 那次估算 3.4861 CNY、一次调用都没发出去，改成 10 之后整轮只花 0.4702。第一轮改完再跑，0.1 那次变成花了 0.0382、评审 0 条、4 个文件全进未评审：「这还是不对啊」。要求整理预算逻辑；随后进一步问「不做预算呢？直接累计，超过就停止」——最终选定的是中间档：删掉估算，只保留精确的输出封顶与收尾预留。

**步骤**：
- 对着 run `e43e23dd8474aa72` 的日志定位：chunk 1 跑满 6 轮、花掉 0.0382，第 7 轮被拦下后 `chunks: []`，6 轮工作连同文件一起丢进未评审。每轮 usage 是 `input 17500 / cached 17024`，厂商收 0.0038，而 `estimate` 把 `cached_input_tokens` 写死 0，按全新鲜算成 0.0525
- 先按观测到的缓存命中率给输入计价（`Budget` 记本 run 已结算的 usage），跑通了；随后按「不做预算、直接累计」的追问**把估算整个删掉**——`estimate`、命中率跟踪、`usage` 字段一并移除
- `allow(ceiling, reserve)` 只剩精确算术：`min(模型上限, 剩余 ÷ 输出单价 − 预留)`，两边都是输出 token 所以预留是一次减法；低于 `LEAST_USEFUL_OUTPUT_TOKENS`（1024）拒绝。删掉 `check` 与 `BudgetError::Exhausted.estimate` 字段，调用前只剩这一道闸
- `StageContext::authorize(&mut request, reserve)` 把允许量写进请求；review 的调查轮传 `CONCLUDING_OUTPUT_TOKENS`（4096），收尾轮与 merge 传 0。`Request::estimated_input_tokens` 只剩上下文检查在用
- review 循环：预算拒绝且已跑过至少一轮时，改走 `conclude` 那条路（撤检视工具、只留交付工具）把已查到的交出来；`ChunkRun.stopped` 只在连收尾都发不出时置位。收尾过的分片留在 `chunks` 并记 `cut_short`，未评审清单从下一片算起
- 开局那一轮不留 reserve——实测留了之后 0.1 预算连第一次调用都发不出（committed 0.0971 > 0.1）
- `Summary` 加 `stopped` 字段，停止原因不再借 `unscored_reason` 转述
- 夹具加 `billing(usage)` 让脚本回复能真的花钱，加 `with_price`；新增用例覆盖 reserve、地板、以及「中途没钱改为收尾」
- 真实复跑：0.1 CNY 下 10 轮调查 → 收尾轮交出 2 条 major 发现 → 下一个文件首次调用被拒。**0.1067 / 0.1000**，未评审 3 个（原来 0 条发现、未评审 4 个、只花 0.0382）
- `cargo test` 全绿、`cargo clippy --all-targets -- -D warnings` 零警告；design.md 预算段与验收项照真实输出更新

**决策**：
- **不预测单次调用花费，只累计真实账单。** 预测错了两次：先按满额思维链（384K × 9/1M = 3.46 CNY）记账，一个 0.1 的预算连第一次调用都发不出；改成按观测命中率估输入后又在收尾轮翻车——前十轮命中率 90%+，收尾那轮只有 39%（20739 里命中 8064），差四倍。**命中率本身不稳定，当不了闸门。**
- **只留没有猜测成分的那一半。** 输出单价已知且从不走缓存，`剩余 ÷ 输出单价` 是精确除法；算出来的数写进请求的 `max_output_tokens`，厂商是被约束住而不是被信任。输入不进闸门，回复之前它到底多贵不可知
- **接受一次调用的输入作为超支上界。** 实测 0.1 的预算收在 0.1067，多出的 0.0067 全来自收尾轮的输入。换来的是没有任何一次调用因为猜错被误拒；越线量随对话长度增长，要收紧就调分片上限
- **留一笔给收尾，且开局不留。** 花了钱却什么都没换回来是最坏的结果；但开局那轮还没查到东西，停在它前后同样是空手，留了反而让 run 起不了步
- **低于 1024 token 的输出额度直接拒绝。** 否则最后一点钱买回来的只是一句被截断的话
- 为什么不是要求预算至少够一次满额输出：那会把 `budget_per_run` 变成约 3.5 CNY 的地板，而整轮实耗往往不到 1 元
- 为什么不是纯累计、连输出也不封顶：超支上界会变成一整次调用，记录里出现过单次 `output_tokens=37406 / spent=0.3447`，理论上限 3.46 CNY，在 0.1 的预算上是 3.4～35 倍；而封顶是精确除法，不花任何猜测成本
- **调用前拦截原本是自定的硬约束，不是题目要求**（见 [002](002-reviewbot-design.md) 「预算、恢复与清理」），所以放宽成「按真实账单累计、允许越线一次输入」是可以做的取舍，`design.md` §6 照实改写
